# Безопасная совместная работа с backlog.md

## Problem Frame

Несколько агентов работают в одной папке и изменяют один `backlog.md` исключительно через `bl`; человек может пользоваться `bl gui`. Нужно исключить потерю параллельных изменений и двойной успешный захват задачи, сохранив Markdown источником истины и установку одним скриптом без сторонних зависимостей.

Проверено в `bl`: Python-команды читают файл и затем перезаписывают его без блокировки, Swift GUI атомарно сохраняет файл, но не защищает всю операцию чтение–изменение–запись. Обе реализации используют номера строк; `take` не проверяет предыдущий статус. GUI также самостоятельно редактирует и переставляет задачи.

---

## Actors

- A1. Агент: просматривает, добавляет, забирает и завершает задачи через CLI.
- A2. Человек: добавляет и редактирует задачи, меняет статусы и порядок, архивирует через CLI или GUI.
- A3. API-провайдер: опционально предлагает осмысленный ID новой задачи; не отвечает за уникальность или хранение.

---

## Key Flows

- F1. Первое обращение к существующему бэклогу
  - **Trigger:** Просмотр через `bl` / `bl v`, открытие GUI или изменяющая операция.
  - **Actors:** A1, A2.
  - **Steps:** Под общей блокировкой перечитать файл, найти задачи без ID в активной и архивной секциях, присвоить локальные случайные ID, атомарно сохранить только при необходимости. При конфликтующих существующих ID сообщить об ошибке, не исправляя их молча.
  - **Outcome:** У задач есть постоянные ID; повторное обращение не меняет файл без необходимости.
  - **Covered by:** R1–R5, R8.
- F2. Добавление новой задачи
  - **Trigger:** `bl add` или добавление в GUI.
  - **Actors:** A1, A2, опционально A3.
  - **Steps:** Сохранить явно переданный конечный `#id`; иначе получить кандидата от модели при наличии API-ключа или сгенерировать локально. Затем под блокировкой перечитать бэклог, проверить уникальность, при коллизии сгенерированного кандидата выбрать случайный свободный ID и записать задачу. Сбой API не препятствует добавлению.
  - **Outcome:** Задача добавлена с уникальным ID без потери чужих изменений.
  - **Covered by:** R1–R7, R12.
- F3. Конкурентный захват
  - **Trigger:** Два агента вызывают `bl take refreshDesign`.
  - **Actors:** A1.
  - **Steps:** Каждый выполняет поиск по ID и проверку статуса внутри блокировки. Первый переводит `[ ]` в `[>]`; второй видит занятость и получает неуспех.
  - **Outcome:** Только один агент начинает работу после успешного захвата.
  - **Covered by:** R1, R9, R10, R13.

## Requirements

**Транзакции и общая реализация**

- R1. Все изменяющие операции CLI и GUI сериализуют весь цикл «прочитать актуальное состояние → проверить условия → изменить → сохранить». Блокировка относится к одному физическому бэклогу, а не к отдельной задаче.
- R2. Сохранение атомарно для читателей: они видят целую старую либо целую новую версию, но не пустой или частично записанный файл. Ошибка чтения существующего файла не должна трактоваться как пустой бэклог и приводить к его перезаписи.
- R3. Блокировка кратковременная: не удерживается во время работы агента, пользовательского редактирования или сетевого запроса. Завершение процесса освобождает блокировку; ожидание чужой блокировки ограничено и при превышении возвращает понятную ошибку без изменений.

**Идентификаторы**

- R4. ID хранится видимым последним токеном описания: `- [ ] Описание #refreshDesign`. Он постоянен при смене статуса, редактировании текста, перестановке и архивировании. Уникальность проверяется по активной и архивной секциям совместно, под блокировкой.
- R5. Явно указанный ID сохраняется, в том числе длиннее шести символов. Автоматически генерируемые ID имеют длину 5–6 символов. Явный повтор занятого ID вызывает ошибку без записи; коллизия автоматически предложенного ID разрешается локальной генерацией другого свободного ID.
- R6. При добавлении без явного ID наличие `OPENAI_API_KEY` или `ANTHROPIC_API_KEY` включает генерацию короткого осмысленного ID по описанию задачи быстрой дешёвой моделью доступного провайдера. CLI и GUI используют одинаковые правила. Без ключа используется случайная строка.
- R7. Таймаут, ошибка API, некорректный ответ или коллизия ответа модели приводят к локальному случайному ID, а не к отказу добавления. Не нужны повторные сетевые запросы для разрешения коллизии. Провайдеру передаётся только необходимое описание новой задачи, не весь бэклог; ключи не записываются в Markdown и диагностический вывод. Вывод модели рассматривается только как кандидат ID, не как команда.
- R8. При первом обращении, включая просмотр, старым задачам без ID автоматически присваиваются локальные случайные ID. Это касается активных задач и архива; миграция не вызывает API и не меняет смысл, статус или порядок задач. Несколько параллельных первых обращений не переназначают уже записанные ID. Отсутствующий файл при простом просмотре не требуется создавать.

**Команды и GUI**

- R9. `take`, `done`, `untake` принимают ID без решётки: `bl take refreshDesign`. Поиск однозначный; неизвестный ID и попытка изменить архивную задачу дают ошибку, а не обращение к другой задаче.
- R10. `take` успешен только для задачи со статусом `[ ]`; проверка и переход в `[>]` выполняются в одной транзакции. Для уже занятой или завершённой задачи команда возвращает ненулевой код без изменений. Это правило действует и при обращении по номеру.
- R11. Старый синтаксис `bl take <num>` и числовые аргументы существующих команд сохраняются. Они означают текущий номер строки, не постоянную ссылку. README, справка и инструкция агентам предупреждают: между просмотром и командой номер может устареть и указать на другую задачу. Проверка ревизии для старого синтаксиса не требуется. Полная гарантия правильного выбора относится к обращениям по ID.
- R12. GUI идентифицирует выбранные задачи по ID и не записывает устаревший снимок всего списка. При сохранении текста, который другой участник уже изменил, GUI сообщает о конфликте вместо молчаливого затирания. Операции изменения статуса, порядка и архива применяются к свежему состоянию под общей блокировкой.
- R13. Инструкции из `bl setup` и сценарий `bl run` направляют агента использовать ID и начинать работу только после успешного `take`; при конфликте перечитать доступные задачи. Они не обещают безопасность ручных правок файла или устаревших числовых ссылок.

## Acceptance Examples

- AE1. **Covers R1, R2, R5.** Несколько параллельных добавлений из CLI и GUI оставляют в файле каждую успешно добавленную задачу ровно один раз, с уникальным ID; другие строки не теряются.
- AE2. **Covers R9, R10.** Два одновременных `take refreshDesign` для свободной задачи дают один успешный результат и один отказ. Повторный `take` завершённой задачи не возвращает её в работу.
- AE3. **Covers R4, R9, R11, R12.** Между просмотром и командой выполнен `purge` или перестановка. Обращение по ID и действие GUI затрагивают исходную задачу; числовой аргумент по-прежнему означает текущую строку и не имеет этой гарантии.
- AE4. **Covers R5–R7.** Модель вернула уже занятый `login`, недопустимый ответ или не ответила вовремя. Задача всё равно добавляется со свободным случайным ID длиной 5–6 символов. Если пользователь явно передал занятый `#login`, добавление отклоняется.
- AE5. **Covers R1, R3, R8.** Два процесса одновременно открывают старый бэклог без ID. После миграции все задачи, включая архивные, имеют уникальные стабильные ID; API не вызван, повторное чтение не изменяет файл.
- AE6. **Covers R2, R3.** Процесс принудительно завершён во время транзакции. Другой процесс может получить блокировку; `backlog.md` содержит целую старую либо новую версию, а не обрезанный документ.
- AE7. **Covers R3, R7.** Пока один процесс ожидает ответа модели, другой может выполнить локальную операцию над бэклогом. Общая блокировка не удерживается на сетевом запросе.
- AE8. **Covers R12.** Человек открыл редактор задачи в GUI, затем другой участник изменил её текст. Сохранение старой формы сообщает о конфликте; изменение другой задачи не должно само по себе блокировать сохранение этой.

## Success Criteria

- Параллельные успешные записи через обновлённые CLI и GUI не теряют изменения друг друга.
- Из конкурирующих захватов одной свободной задачи успешен только один, а ID не меняет адресат при перестановках.
- Бэклог остаётся читаемым Markdown; отсутствие API-ключей или доступности провайдера не ломает работу.
- Старый числовой интерфейс сохранён с честно описанными ограничениями.
- Реализация проверяется многопроцессными тестами; тестирование API-веток не требует реальных ключей или платных запросов.

## Scope Boundaries

- Только одна локальная папка и один физический файл; не согласование разных worktree, клонов или машин, не сетевые файловые системы.
- Все участники используют обновлённый `bl`. Прямые правки редактором, Git checkout во время транзакции и старые версии `bl`, игнорирующие блокировку, не защищены.
- Без БД, демона и сторонних Python-зависимостей.
- Без владельцев задач, токенов владения, lease/heartbeat и автоматического освобождения зависших задач. `take` защищает переход состояния, но `done` не аутентифицирует владельца.
- Автовыбор следующей задачи (`bl take` без аргументов) обсуждался как возможное расширение; не является обязательной частью согласованного объёма.
- Гарантия атомарной видимости и устойчивости к завершению процесса не равна гарантии сохранения последней записи после потери питания.

## Key Decisions

**Подтверждено пользователем:** один общий файл, изменения через `bl`; видимые `#id`; генерируемые ID длиной 5–6 символов; осмысленная генерация при наличии API-ключа; сохранение числового синтаксиса с предупреждением; новый синтаксис без `#`; автоматическая локальная миграция при первом обращении.

**Рекомендуемая техническая основа:** отдельный постоянный `.backlog.lock` с `flock`, который не удаляется после операции; временный файл в той же директории и атомарный `os.replace`. Не блокировать сам `backlog.md`, поскольку при замене меняется inode. Предпочтительно направить записи GUI через общую Python-реализацию, а не поддерживать две транзакционные реализации.

**Рабочие правила для планирования:** различать регистр явных ID и сохранять написание (`refreshDesign`); разрешать буквы ASCII в начале и буквы/цифры/`_`/`-` далее. Чисто цифровые ID не использовать, чтобы не конфликтовать с номерами строк. Генерируемые ID также начинаются с буквы. Эти правила предложены как простая однозначная грамматика, а не как отдельно запрошенное расширение формата.

## Dependencies / Assumptions

- Основной локальный сценарий — macOS с GUI, для CLI также учитывать POSIX-системы. Объём поддержки Windows нужно проверить до выбора механизма блокировок.
- Сетевое добавление может быть медленнее локального; ограниченное время ожидания и случайный fallback обязательны.
- Дешевизна и скорость моделей меняются; нельзя обещать абсолютный минимум задержки без измерений. При выборе ориентироваться на актуальные официальные модели для коротких простых ответов, без ненужного reasoning.
